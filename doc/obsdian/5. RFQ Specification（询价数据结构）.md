# English

## Supabase Database Schema

To implement this RFQ structure within our Supabase (PostgreSQL) backend, the data is captured into the following unified relational table. 

### `rfqs`
Captures user quoting forms submitted from the website interface. This consolidates user identity, parameter specs, and routing lists into a single, highly-normalized table.

| Column Name | Type | Description |
| :--- | :--- | :--- |
| `id` | `uuid` | Primary Key. |
| `first_name` | `text` | Requestor's First Name. |
| `last_name` | `text` | Requestor's Last Name. |
| `company_name` | `text` | Optional Company Name. |
| `country` | `text` | Requestor's Country Location. |
| `email` | `text` | Requestor's Email. |
| `is_business_email`| `boolean`| True if domain is non-generic (not Gmail/Yahoo/etc). |
| `industry` | `integer` | Foreign Key/Identifier referring to the `industries` dictionary. |
| `quantity` | `text` | Quantity scale required. |
| `delivery_timeline`| `text` | Urgency / deadline for the project. |
| `product_type` | `text` | General equipment type description limit. |
| `parameters` | `jsonb`| A dynamic JSONB object storing `hot_fluid`, `cold_inlet_temp`, `design_pressure` and other critical specs. |
| `additional_notes` | `text` | Free-form user memo. |
| `manufacturers_sent_list` | `text[]` | Array of manufacturer IDs that successfully received constraints routing. |
| `is_stealth` | `boolean`| If true, anonymize identity details when sending initial requests to suppliers. |
| `created_at` | `timestamp`| Request lifecycle tracking timestamps. |
| `updated_at` | `timestamp`| Request lifecycle tracking timestamps. |

*(Note: If attachments like specifications or technical drawings are supported in future modifications, they should follow the `asset_type` unified schema structure, or be linked via a separate relations table if decoupled from general assets.)*

# 中文版本

## Supabase 数据库表结构 (Database Schema)

为了在 Supabase (PostgreSQL) 后端中实现上述 RFQ 流程，表单数据将被记录到以下高度范式化的统一关系表中。

### `rfqs` (用户询价统合表)
保存任何从网页前端发出的询价表单记录 (Request for Quotation)，充当买方需求和工厂供给之间的桥梁。在 V2 结构中剥除了大量松散字段，由 JSONB 参数字段承接了动态多变的工况要求。

| 列名 | 类型 | 描述 |
| :--- | :--- | :--- |
| `id` | `uuid` | 主键。 |
| `first_name` | `text` | 采购商名。 |
| `last_name` | `text` | 采购商姓。 |
| `company_name` | `text` | 采购商公司名称（选填）。 |
| `country` | `text` | 采购商所在国家。 |
| `email` | `text` | 验证过后的确认邮箱。 |
| `is_business_email`| `boolean`| 以此作为线索判别该询盘来源质量（非 Gmail/QQ 单独核算）。 |
| `industry` | `integer` | 关联至全局词典字典表 `industries` 中的具体 ID。 |
| `quantity` | `text` | 需求采购量区间。 |
| `delivery_timeline`| `text` | 期望交付时间表/紧急程度区间。 |
| `product_type` | `text` | 所需设备类型描述（如可拆板换等）。 |
| `parameters` | `jsonb` | 极高含金量的核心动态数据载体。无论用户填入多少冷热测流体工况或是设计压力极值，统统归于此列记录。 |
| `additional_notes` | `text` | 补充用户留言与额外需求。 |
| `manufacturers_sent_list` | `text[]` | 推发名单阵列，记录下这封询价最终发送给了哪些制造商的主键副本（基于他们匹配的能力）。 |
| `is_stealth` | `boolean`| 是否在初期将用户隐身，防止邮箱外泄遭到大量骚扰。 |
| `created_at` | `timestamp` | 生命周期管理追踪时间戳。 |
| `updated_at` | `timestamp` | 生命周期管理追踪时间戳。 |

*(注: 若后续决定进一步集成技术文件打包上传的功能，文件路径可以复位引入统一的 asset 设计范式进行二次扩展绑定。)*
